## 一、产品需求(PRD部分-前端视角)

### 1.1 用户角色与核心Persona

**Persona A:「精打细算的种草党」(18-24岁)**
- 学生/初入职场,价格敏感,决策链长,反复比价、看评价、找优惠券
- 高频使用手机端,碎片时间浏览,容易被首页banner/直播/短视频种草内容吸引
- 核心诉求:低价、大促活动、满减/优惠券叠加、真实用户评价

**Persona B:「品质敏感的成熟消费者」(25-35岁)**
- 已有稳定收入,更看重正品保障、成分安全、复购便捷性
- 决策快但极度关注"是否假货",会主动查防伪信息、品牌授权、物流时效
- 核心诉求:正品验证入口、회员积分/专属客服、快速复购(常购清单)

**Persona C(可选补充):「送礼/临时采购型」**
- 因节日/送礼临时下单,关注礼盒装、包装展示、加急配送
- [待确认] 是否需要为该人群单独设计"礼品模式",初期建议并入P1功能而非单独角色体系

### 1.2 核心功能模块清单

**P0 / MVP(必须)**
- 首页(banner、分类入口、推荐商品流)
- 商品分类浏览
- 商品搜索(关键词搜索)
- 商品详情页(含SKU选择、图文详情、基础评价展示)
- 购物车(加购/改数量/删除/选中结算)
- 下单结算流程(地址选择、运费展示、下单)
- 支付跳转与支付结果页(前端只负责跳转第三方支付并接收回调状态)
- 登录/注册(手机号+验证码)
- 个人中心首页
- 订单列表与订单详情
- 基础的loading/空状态/错误状态处理

**P1(第二阶段)**
- 收货地址管理(增删改、默认地址)
- 收藏夹/我的关注
- 优惠券中心(领取、我的优惠券、结算时选用)
- 商品评价发布(含图片上传)
- 正品验证入口(防伪码查询页,展示层面对接后端查询接口)
- 会员积分/等级展示
- 售后/退款申请流程
- 搜索结果筛选与排序(价格区间、销量、品牌)

**P2(远期)**
- 智能个性化推荐流(首页信息流)
- 直播购物/短视频种草
- AR试妆/肌肤测试
- 社区UGC(种草笔记)
- 客服在线聊天(可先接入第三方SDK而非自研)
- 多语言/多币种(如涉及跨境)

### 1.3 关键业务流程(前端交互视角,不涉及后端逻辑)

**流程1:浏览-加购-结算-支付**
首页/分类/搜索 → 商品详情页(选SKU、看评价) → 加入购物车(Toast反馈) → 购物车页(勾选商品) → 结算页(选地址、选优惠券、确认金额) → 调用支付接口跳转第三方支付页 → 支付回调后前端轮询/回跳判断状态 → 展示支付结果页 → 跳转订单详情

**流程2:注册/登录**
点击"我的"未登录态 → 弹出登录页(手机号输入) → 点击获取验证码(60秒倒计时,防重复点击) → 输入验证码提交 → 成功后写入本地token/用户信息 → 跳转登录前页面或首页

**流程3:搜索与筛选**
首页搜索框/搜索历史 → 输入关键词联想(如有) → 搜索结果列表 → 筛选(价格区间/销量/新品)+排序 → 点击商品进入详情页 → 返回时保留筛选状态(前端路由参数或本地缓存)

**流程4:售后/退款申请**
订单详情页 → 点击"申请售后" → 选择售后类型(仅退款/退货退款) → 填写原因+上传凭证图片 → 提交申请 → 售后进度查看(前端展示状态机:待审核/处理中/已完成/已拒绝)

## 二、前端技术架构

### 2.1 技术栈选型

- 框架:**Vue 3 + TypeScript**(生态成熟、组件化清晰,团队上手成本低)
- 构建工具:**Vite**
- UI组件库:**Vant 4**(移动端优先,美妆电商用户以手机端为主;若需兼容PC端管理态展示,补充少量自定义组件而非引入Element Plus,避免双组件库增加体积)
- 状态管理:**Pinia**
- 路由:**Vue Router 4**
- HTTP客户端:**Axios**
- CSS方案:**Sass + CSS变量**(便于主题色统一管理),布局采用 `postcss-px-to-viewport` 或 `rem` 自适应
- 代码规范:ESLint + Prettier + Husky(commit前校验)
- [待确认] 是否需要小程序端同步(如需,建议后续用uni-app重构而非本阶段兼顾,避免过度设计)

### 2.3 前端状态管理方案

**存入全局Store(Pinia)**
- 用户信息与登录态(token、用户基础资料)
- 购物车数据(商品列表、选中状态、总价——因需跨页面共享:购物车页/结算页/详情页角标)
- 全局UI状态(全局loading计数、全局Toast队列、网络异常提示)
- 收货地址列表(结算页/地址管理页共享)

**存入组件内部(局部state)**
- 表单临时输入值(登录框、地址编辑表单、评价表单)
- 列表页筛选/排序条件(可选配合路由query持久化,但不必全局共享)
- 弹窗/抽屉的开关状态
- 分页/加载更多的游标状态

### 2.4 前端路由设计

- **懒加载**:所有页面组件使用 `() => import('...')` 动态导入,按路由分包
- **路由守卫**:
  - 全局前置守卫校验 `meta.requiresAuth`,未登录跳转 `/login?redirect=xxx`
  - 登录成功后读取redirect参数回跳
- **404兜底**:通配符路由 `*` 跳转 `/404`
- **滚动行为**:切换页面时重置scrollTop,返回列表页保留滚动位置(scrollBehavior + keep-alive缓存列表页)

## 三、UI/UX设计规范

### 3.1 页面布局框架

- 移动端为主:顶部导航(搜索框/返回按钮) + 内容区(可滚动) + 底部Tabbar(首页/分类/购物车/我的,4个一级入口)
- 详情页/结算页:无Tabbar,采用"沉浸式顶部+底部操作栏"结构(如详情页底部固定"加入购物车/立即购买")
- 弹层类交互(SKU选择、地址选择)统一使用底部弹起的Popup/ActionSheet,符合移动端习惯

### 3.2 设计风格与色彩体系

- 风格定位:清新、精致、略带温度感,契合美妆调性,避免过度促销感的大红大绿
- 主色:珊瑚粉 `#FF6F91`(用于按钮、价格强调、品牌标识)
- 辅色:奶油白 `#FFF8F5`(背景)、深灰 `#333333`(正文文字)、浅灰 `#999999`(辅助文字)
- 强调色:金色 `#D4A056`(用于"正品保障""会员"等信任标识,提升质感)
- 状态色:成功 `#52C41A`、警告 `#FAAD14`、错误 `#F5222D`
- 字体:系统默认字体栈(`-apple-system, "PingFang SC", "Microsoft YaHei"`),避免自定义字体增加加载体积
- 字号规范:标题18-20px,正文14-15px,辅助文字12px
- 间距规范:基础8px网格(8/16/24/32px),卡片圆角统一12px

## 四、前端交互与逻辑

### 4.1 核心交互流程的文字描述(全链路)

用户首次打开网站 → 首页展示推荐商品与活动banner(游客态可浏览) → 用户搜索"洗面奶" → 进入搜索结果页,按销量排序并筛选价格100元以下 → 点击某商品进入详情页 → 查看图文详情与评价后选择规格"150ml" → 点击"加入购物车"(若未登录,加购操作可先在本地/游客购物车保存,登录后合并;或直接拦截登录,取决于[待确认]业务决策,建议MVP阶段允许游客加购,结算时才强制登录) → 继续浏览加购第二件商品 → 进入购物车页勾选两件商品 → 点击"去结算" → 若未登录跳转登录页,登录后回跳结算页 → 结算页选择收货地址(首次需新增地址)、选择可用优惠券 → 确认总价后点击"提交订单" → 前端调用创建订单接口获得订单号,再调用支付接口跳转支付 → 支付完成后跳回支付结果页展示成功状态 → 用户进入"我的订单"查看订单状态 → 收货后进入订单详情点击"确认收货" → 随后跳转发表评价页完成评价闭环。

### 4.2 表单校验规则

**登录/注册(手机号+验证码)**
- 手机号:11位数字,正则 `^1[3-9]\d{9}$`,非法格式实时红字提示"请输入正确的手机号"
- 验证码:6位数字,倒计时60秒内禁用"获取验证码"按钮并显示倒计时
- 用户协议:未勾选时提交按钮禁用或点击时提示

**收货地址表单**
- 收货人姓名:2-20字符,不可为空
- 手机号:同上正则校验
- 省市区:必选,使用级联选择器,不可跳级
- 详细地址:5-100字符,不可为空
- 至少保留一个默认地址,删除默认地址前需二次确认

**评价表单**
- 星级评分:必选(默认5星或强制点击选择)
- 文字内容:5-500字符(可设最低字数要求以保证评价质量)
- 图片:最多9张,单张不超过5MB,格式限制jpg/png,上传前前端压缩

**优惠券兑换码(若有)**
- 输入框限制大写字母+数字,长度按后端规则(如8-12位),前端仅做格式初筛,真实性由后端校验

**结算页**
- 必须选中收货地址才可提交
- 购物车/结算商品数量必须≥1

### 4.4 页面状态处理

**Loading状态**
- 首屏/列表页:骨架屏(Skeleton),模拟卡片轮廓
- 局部操作(加购/提交):按钮内loading spinner+禁用防重复点击
- 全局请求:顶部细进度条或Vant自带Loading遮罩(仅用于阻塞性操作如提交订单)

**空状态**
- 购物车为空:插画+文案"购物车空空如也"+"去逛逛"按钮跳首页
- 搜索无结果:插画+文案"没有找到相关商品"+推荐商品
- 收藏/订单列表为空:统一Empty组件,不同文案配置

**错误状态**
- 网络请求失败:Toast提示"网络异常,请重试" + 页面内提供"点击重试"按钮
- 接口业务报错(如库存不足):按接口返回message原文展示Toast,不做前端二次包装
- 页面级崩溃/404:跳转404兜底页,提供返回首页按钮

## 五、API调用方案

### 5.1 API调用封装方案

- 基于Axios创建统一实例,配置baseURL(通过环境变量区分dev/test/prod)、超时时间(建议10s)
- **请求拦截器**:自动携带token(Header中Authorization);对特定请求(如提交订单)做防重复提交标记
- **响应拦截器**:
  - 统一解构后端返回结构(如 `{code, data, message}`),`code!==0`时统一走错误处理分支
  - token失效(如401)时清除本地登录态并跳转登录页
  - 网络错误/超时统一Toast提示,不逐个页面重复写错误处理逻辑
- 全局loading计数器:请求发出时+1,结束时-1,归零时关闭全局loading(仅用于配置了 `showLoading: true` 的请求)
- 取消重复请求:对同一接口在上一次请求未返回时自动取消(基于AbortController),避免搜索输入等场景的请求堆积
- 按业务模块封装API方法(如 `getProductDetail(id)`、`createOrder(payload)`),视图层不直接调用axios

### 5.3 本地Mock方案

- 开发阶段使用 **vite-plugin-mock**(与Vite无缝集成,按环境变量开关),在 `mock/` 目录下按模块编写mock文件,拦截对应接口路径返回预设JSON

## 六、非功能性需求(前端部分)

### 6.1 性能要求

- 首屏加载时间:目标在4G网络下 ≤ 2秒(可感知内容出现),弱网(模拟3G)下提供骨架屏保证不空白
- 图片懒加载:商品列表图片使用原生 `loading="lazy"` 或 `vant Lazyload`,首屏外图片延迟加载
- 路由懒加载:所有非首页路由动态导入,按页面分chunk
- 打包体积控制:单个初始chunk(vendor)控制在500KB以内(gzip前),大型组件(如图片裁剪/富文本)按需异步加载;定期用 `rollup-plugin-visualizer` 检查体积

### 6.2 兼容性要求

- 浏览器支持:iOS Safari 12+、Android Chrome 8+、微信内置浏览器(X5内核) —— **微信内浏览器为重点兼容对象**,因目标用户群体高频通过微信分享/朋友圈访问

- 不特别兼容PC端旧版IE浏览器(美妆电商用户以移动端为主,[待确认] 若确有PC端需求,建议做响应式而非另开PC站)
- 安全区适配:iPhone X系列以上机型底部Tabbar/固定按钮需适配 `safe-area-inset-bottom`

### 6.3 用户体验要求

- 页面切换动画:同级页面左右滑动过渡,详情/弹层类页面底部弹起动画,统一在router的transition中配置,避免每个页面单独实现
- 操作反馈:所有异步操作(加购/提交/收藏)均有Toast即时反馈,按钮点击有loading态防重复提交
- 骨架屏:首页、商品列表、商品详情、订单列表等首次加载均使用骨架屏而非纯spinner,降低用户等待焦虑感
- 下拉刷新/上拉加载更多:列表类页面统一使用Vant的PullRefresh/List组件,保持交互一致性

二、前端技术架构
2.1 技术栈选型(前端框架、UI组件库、状态管理、路由、HTTP客户端、构建工具)
- 框架：React + TypeScript（理由：生态丰富、组件复用和社区支持强，便于按需扩展）。  
- 构建工具：Vite（开发体验快、构建速度快）。  
- 路由：react-router-dom v6（声明式路由、支持嵌套路由与懒加载）。  
- 状态管理：组合方案——React Query（TanStack Query）管理后端数据缓存/同步，Zustand 管理本地全局 UI/轻量状态（cart 本地临时态可用Zustand持久化）；避免 Redux 的过度设计。  
- UI 组件库：Ant Design Mobile（移动优先）+ Tailwind CSS（快速样式定制），商业项目可定制主题覆盖组件库样式。  
- HTTP 客户端：axios（配合自定义封装与拦截器）。  
- 其他：react-hook-form（表单处理），msw（Mock Service Worker）用于开发Mock，react-i18next（若需多语言），sentry/bugsnag（生产监控/错误上报）。

2.2 项目目录结构
- src/  
  - main.tsx（入口）  
  - App.tsx（路由容器）  
  - pages/（路由页面，每个页面子目录）  
    - Home/ Listing/ Product/ Cart/ Checkout/ Auth/ User/ Search/ Help/...  
  - layouts/（通用布局：MainLayout、AuthLayout、UserLayout）  
  - components/（可复用组件：ProductCard、ImageCarousel、SpecPicker、Skeleton等）  
  - hooks/（自定义hook：useCart、useAuth、useInfiniteScroll）  
  - services/（API调用封装文件按域：product.ts、auth.ts、order.ts）  
  - store/（Zustand store定义：useGlobalStore、useCartStore）  
  - queries/（React Query keys & hooks：useProducts、useProduct）  
  - types/（TypeScript 类型定义）  
  - utils/（工具函数：formatPrice、debounce、analytics）  
  - assets/（静态资源与占位图）  
  - styles/（全局样式、tailwind 配置）  
  - mock/（msw handlers 与本地 JSON fixtures）  
  - tests/（单元/集成测试）  
  - config/（环境配置、常量）  

2.3 前端状态管理方案(哪些数据存全局store，哪些存组件内部)
- 全局持久化store（Zustand，localStorage持久化必要项）：购物车（商品列表、数量、价格快照）、Auth token 与用户基础信息（非敏感字段）、用户偏好（地址默认、展示偏好）、心愿单ID集合（如后端同步时）和全局UI状态（底部Tab显隐、主题色）。  
- React Query 管理服务器数据缓存：商品列表、商品详情、分类树、搜索结果、优惠券列表、订单列表与订单详情（自动缓存/失效）。  
- 组件本地状态：模态框显隐、规格选择临时态、表单输入（由 react-hook-form 管理）、分页当前页、筛选暂存（在结果页内存储）。  
- 不要将大量后端数据放入全局同步store，以避免复杂同步逻辑；优先使用 React Query。

2.4 前端路由设计(路由守卫、懒加载策略)
- 路由守卫：在路由层实现 ProtectedRoute 组件，检查 auth token 或 user info，未登录则 redirect 到 /auth/login?redirect=target；对敏感页面（/checkout,/pay,/user/*）强制校验。  
- 懒加载策略：页面级懒加载（React.lazy + Suspense），优先预加载首页、分类页资源；对高频入口（首页关键组件、底部导航）采用预取（link rel=preload/preconnect 或 router prefetch）。  
- 按需加载组件和图片：ProductDetail、Checkout、UserCenter 等单独 chunk，列表页图片按需懒加载并使用占位骨架。  
- 错误边界：在路由层包裹错误边界组件并显示友好错误或重试按钮。

三、UI/Ux设计规范
3.1 页面布局框架(整体布局结构)
- 移动优先单列布局为主，顶部固定搜索栏/品牌Logo，主要内容区域滚动，底部固定导航（首页、分类、购物车、我的）; 在大屏（>1024px）采用两列布局：左侧筛选/导航、右侧商品列表/详情。  
- 通用页面结构：Header（含搜索/返回/分享）、Content（可滚动，卡片化内容）、Sticky Action Bar（商品页加入购物车/立即购买）、Footer（版权/客服）。  
- 使用一致的内边距与间距系统（见 3.2）。

3.2 设计风格与色彩体系(主色/辅色/字体/间距规范)
- 设计风格：轻盈、女性化且现代，照片为主，卡片化信息展示，强调清晰的购买路径与信任元素（正品保障徽章）。  
- 主色（Primary）：温和粉色 #FF6B88（用于CTA按钮、促销标签）。  
- 辅色（Secondary）：柔和紫 #A77BFF（辅助CTA/高亮）、清新绿 #27AE60（成功/打勾）。  
- 中性色：深灰 #222831（主文本）、中灰 #666666（次文本）、浅灰 #F5F6F8（背景）、边框灰 #E6E9EE。  
- 警示色/错误色：橙色 #FF9F43 / 红色 #FF4D4F。  
- 字体：移动优先使用系统汉字字体组合（"PingFang SC", "Hiragino Sans GB", "Microsoft Yahei", sans-serif），英文字体 fallback 为 "Inter"。  
- 字体规模与间距（示例）：h1:20px, h2:18px, body:14px, small:12px；基线间距采用4px刻度；组件圆角统一 8px（卡片6px，按钮圆角12px可选）。  
- 图像规范：主图建议 750px 宽（移动端），使用 srcset 提供多分辨率资源；图片展示比例在列表为1:1或4:5，详情页可用 16:9 + 1:1 组合。  

3.3 所有页面清单及功能说明(每个页面需描述:页面核心元素、主要交互行为、跳转逻辑)
- 首页 (/)：核心元素：轮播 Banner、分类入口卡、限时秒杀/促销栏、推荐商品模块、品牌专区、底部导航。主要交互：点击商品/券位跳转详情或列表，横向卡片支持滑动，Banner 支持跳转到专题页或商品。跳转：商品->/product/:id，分类->/category/:id，专题->/listing?tag=。  
- 分类页 (/category/:id)：核心元素：类目树、筛选入口、热门子类目。主要交互：点选子类目更新列表，点击“筛选”打开筛选抽屉。跳转：选择子类目->/listing，商品->/product/:id。  
- 商品列表/搜索结果 (/listing,/search)：核心元素：商品卡片（图、价、促销）、筛选条、排序菜单、分页/无限加载。主要交互：筛选/排序触发 API 请求并显示骨架，商品卡片点击进入详情，长按或心形触发收藏（需登录）。跳转：商品->/product/:id。  
- 商品详情 (/product/:id)：核心元素：图片轮播、价格与SKU选择、成分/功效标签、用户评价、相似推荐、分享与客服入口、加入购物车/立即购买按钮。主要交互：选择规格更新价格/库存，滑动图片支持放大，点击评价跳转到评价锚点，点击“加入购物车”弹出加入成功提示并可去结算。跳转：加入购物车->/cart，立即购买->/checkout?sku=。  
- 购物车 (/cart)：核心元素：商品列表、价格明细、优惠券入口、去结算按钮、批量编辑模式。主要交互：调整数量时立即乐观更新并同步到 store，删除提示确认，选择结算触发登录守卫。跳转：去结算->/checkout。  
- 结算页 (/checkout)：核心元素：收货地址选择/新增、配送方式、发票与备注、优惠券/积分抵扣、价格明细、提交订单。主要交互：选择/新增地址弹出表单，优惠券弹窗选择后实时更新价格，提交订单触发下单API并转至支付页。跳转：提交->/pay/:orderId。  
- 支付页 (/pay/:orderId)：核心元素：支付方式选择、支付倒计时、支付结果回调。主要交互：选择支付方式并调用支付SDK/跳转第三方，支付回调后展示结果并跳转订单详情。跳转：支付成功->/user/order/:id。  
- 登录/注册 (/auth/login,/auth/register)：核心元素：手机号/邮箱登录、社交/第三方登录按钮、找回密码。主要交互：表单校验、验证码发送倒计时、注册后回跳。跳转：登录成功跳回原目标或首页。  
- 用户中心 (/user)：核心元素：用户信息、快捷入口（订单/地址/优惠券/收藏）、最近浏览。主要交互：点击订单进入订单列表，点击设置进入地址管理。跳转：订单->/user/orders，地址->/user/addresses。  
- 订单列表 (/user/orders) & 订单详情 (/user/order/:orderId)：核心元素：订单状态列表、订单卡、操作按钮（取消/退货/评价）、物流跟踪链接。主要交互：根据状态出现不同操作，申请退货弹出表单并上传图片。跳转：退货/详情内跳转到相应API操作节点或帮助页。  
- 收藏/心愿单 (/user/wishlist)：核心元素：商品网格、批量加入购物车、删除。主要交互：批量操作、商品失效提示。跳转：商品->/product/:id。  
- 帮助/FAQ (/help)：核心元素：问题分类、搜索、在线客服快捷入口。主要交互：点击问题展开答案、跳转客服或工单创建页。  

四、前端交互与逻辑
4.1 核心交互流程的文字描述(用户从进入到完成核心任务的全链路)
- 发现并购买流程（简述）  
  1) 用户从首页或搜索进入商品详情，前端并行请求商品详情、库存与评价数据并渲染骨架到真实数据。  
  2) 用户选择规格并点击“立即购买”，UI进行校验（库存/规格选择），若未登录触发登录守卫并回跳；已登录则调用结算前准备 API（锁库存/创建临时订单）并跳转支付页。  
  3) 支付页面调用支付SDK或返回第三方支付页面，支付完成回调后前端轮询订单状态并展示结果；若超时或失败提供重试与客服按钮。  
- 搜索->筛选->下单（简述）  
  1) 用户输入关键词触发防抖请求显示联想建议；提交搜索后由 listing 页面读取 query 并请求服务端带筛选参数的结果。  
  2) 用户打开筛选抽屉选择多维筛选项，前端保持筛选状态并每次变更触发带条件的 fetch（支持“仅应用”按钮减少请求频率）。  
  3) 找到商品后进入详情并按上述流程下单。  
- 注册->查看订单->申请退款（简述）  
  1) 用户完成注册后自动更新全局用户信息并跳转到注册来源页。  
  2) 在用户中心查看订单详情并选择“申请退货”，弹出退货表单并支持附件上传；提交后前端显示申请成功并在订单详情页挂靠申请记录。

4.2 表单校验规则(涉及表单录入的所有场景)
- 登录/注册：手机号校验中国手机号规则（^1[3-9]\d{9}$），邮箱格式校验，验证码为 4-6 位数字，密码最小长度 8，需包含字母与数字（可选特殊符号）。  
- 地址表单：收件人非空（最长50字符），手机号同上，省市区必填，详细地址最少5字符，邮政编码可选且匹配 6 位数字规则。  
- 提交订单备注：最大 500 字符限制。  
- 退款/售后申请：原因必填，图片上传最大 5 张，每张 <5MB，格式 jpg/png。  
- 评论/评价：评分必填（1-5），文字评论可选但若上传图片建议最少 5 字以上。  
- 所有表单均在前端进行必填与格式校验，并在失败时给出具体错误提示与聚焦到出错字段。

4.3 前端数据模型(前端使用的数据结构定义)
- Product: { id: string; name: string; images: string[]; price: number; marketPrice?: number; salePrice?: number; skuList: SKU[]; rating: number; reviewCount: number; description: string; attributes: Record<string,string>; tags: string[]; stock: number }  
- SKU: { skuId: string; specs: Record<string,string>; price: number; stock: number; barcode?: string }  
- Category: { id: string; name: string; parentId?: string; icon?: string }  
- CartItem: { productId: string; skuId?: string; name: string; image: string; unitPrice: number; quantity: number; selected: boolean }  
- User: { id: string; nickname: string; avatar?: string; phone?: string; email?: string; defaultAddressId?: string }  
- Address: { id: string; receiver: string; phone: string; province: string; city: string; district: string; detail: string; postcode?: string; isDefault: boolean }  
- Order: { id: string; status: string; totalAmount: number; items: CartItem[]; createdAt: string; payInfo?: any; shipment?: { carrier?: string; trackingNo?: string } }  
- Coupon: { id: string; code: string; description?: string; discountAmount?: number; minSpend?: number; validFrom?: string; validTo?: string }  
- Review: { id: string; userId: string; productId: string; rating: number; content: string; images?: string[]; createdAt: string }

4.4 页面状态处理(loading/空状态/错误状态的展示方式)
- Loading：页面级数据使用骨架屏（skeleton）优先显示，次要组件用局部 Spinner。骨架样式与真实布局一致以减少视觉跳动。  
- 空状态：列表/搜索无结果展示图文空状态（CTA 引导返回首页或去逛逛），购物车为空展示引导购买的促销卡片。  
- 错误状态：网络/服务器错误显示全局错误条或错误页，提供“重试”与“联系客服”按钮；对于局部失败（例如评论加载失败）只替换相应模块并允许局部重试。  
- 离线状态：检测到 navigator.onLine=false 时在顶部展示黄色横幅提示离线，禁止提交类操作并缓存用户输入（如评论草稿）。

五、API调用方案
5.1 API调用封装方案(统一的request封装、拦截器、错误处理)
- 使用 axios 创建统一实例 request（baseURL 从环境变量读取）。  
- 请求拦截器：自动附加 Authorization token；对需要签名的请求在 header 加签（若后端要求，前端仅传递后端提供的字段）；公共请求头设为 application/json，上传使用 multipart/form-data。  
- 响应拦截器：统一处理 HTTP 状态码与业务码，401 时触发刷新 token 流程或清除登录态并重定向到登录页；对 5xx 显示统一错误提示并记录到监控。  
- 错误处理：按错误场景区分用户可重试/不应重试；对网络错误提供重试按钮；对幂等 GET 请求使用 axios-retry（短重试策略）配合 React Query retry 控制。  
- 统一返回数据结构转换：将后端的 data 字段解包并在 services 层做最小适配，供 React Query hooks 使用。  
- 日志与上报：在拦截器内收集请求耗时、异常并按采样上报到 Sentry/日志系统。

5.3 本地Mock方案(开发阶段数据模拟方式)
- 使用 Mock Service Worker (msw) 在开发/测试环境拦截网络请求并返回可控 fixture；优点：近似真实网络层、支持按环境切换，便于 React Query 调试。

六、非功能性需求(前端部分)
6.1 性能要求(首屏加载时间、图片懒加载、路由懒加载、打包体积控制)
- 首屏加载时间目标：移动端 4G 环境首屏交互时间 < 2s（尽力达成，依赖 CDN/图片优化）。理由：目标用户以移动端为主，快速响应提升转化率。  
- 图片策略：使用 responsive srcset/AVIF/WebP 优先格式，列表图设置低质量占位图(LQIP)并懒加载；详情页首屏主图预加载。  
- 路由懒加载：页面级代码分割，初始包控制在 150-200KB gzip（建议值，依项目情况调整）。  
- 打包优化：开启 tree-shaking、按需加载组件库、使用自动拆包与压缩，精简 polyfills。  
- 监控：上线后接入 RUM（如 Sentry Performance/Datadog）监测 FCP、LCP、TTI 并配置阈值报警。  
6.2 兼容性要求(浏览器支持范围、移动端适配)
- 浏览器支持：现代浏览器优先支持 Chrome（Android）最新两版、Safari（iOS）最新两版；兼容微信内置浏览器；不必强制支持 IE11。若需企业兼容另行确认。[待确认]  
- 移动端适配：移动优先设计，视窗最小宽度 320px (iPhone SE)、常见宽度 360-412px；采用 rem/响应式单位和弹性图片。  
- 无障碍：基础无障碍支持（语义化标签、按钮可被触控/键盘聚焦、图片 alt、表单 aria 标签）。  
6.3 用户体验要求(页面切换动画、反馈提示、加载骨架屏)
- 页面切换与交互反馈：路由切换用 150-200ms 渐变/滑动过渡；操作性反馈（添加购物车、收藏）使用浮层 toast 与动效确认；按钮在交互时有按压态。  
- 加载骨架屏：列表与详情关键区域使用骨架，避免空白页面感。  
- 表单与错误反馈：即时校验错误提示并聚焦错误项，关键操作（提交订单/支付）有明确 loading 状态与防重提交保护。  
- 易用性：搜索具备模糊匹配与联想词，筛选支持清空与保存常用筛选。

*   **路由守卫 (Navigation Guards)**:

        *   **登录状态检查**: 判断用户是否已登录（检查Pinia store中的token），若访问需要登录的页面但未登录，则重定向至登录页。
        *   **权限检查**: [待确认] 若有不同用户角色和权限，在此进行鉴权判断。
    *   **路由元信息 (Meta Fields)**: 在路由配置中使用`meta`字段标记页面是否需要登录或特定权限，如`meta: { requiresAuth: true, title: '我的订单' }`。
*   **懒加载策略 (Lazy Loading)**:
    *   **按模块/页面懒加载**: 所有 `views` 目录下的页面组件都采用动态导入 `import()` 进行懒加载，将每个页面打包成独立的JS Chunk。
        ```javascript
        // router/index.js 或 modules/*.js
        const routes = [
          {
            path: '/products',
            name: 'ProductList',
            component: () => import('@/views/product/ProductListView.vue'),
            meta: { title: '商品列表' }
          },
          {
            path: '/products/:id',
            name: 'ProductDetail',
            component: () => import('@/views/product/ProductDetailView.vue'),
            meta: { title: '商品详情' }
          },
          // ...其他路由
        ];
        ```
    *   **优点**: 减少首屏加载的JS文件体积，按需加载，提高应用性能。

**四、前端交互与逻辑**

**4.1 核心交互流程的文字描述**

*   **用户首次访问至成功下单全链路**:
    1.  **访问首页**: 用户通过浏览器或广告链接访问网站首页。前端渲染首页布局，加载轮播图、推荐商品等数据，展示给用户。
    2.  **浏览商品**: 用户在首页看到感兴趣的商品，点击图片进入商品详情页。前端根据路由参数请求商品详情API，渲染商品信息、图片、规格、评价等。
    3.  **选择规格与数量**: 用户在详情页选择商品颜色、容量等SKU，并选择购买数量。前端根据选择更新SKU库存和价格显示，并实时校验库存。
    4.  **加入购物车**: 用户点击“加入购物车”按钮。前端通过API将商品及SKU信息发送至后端购物车服务，成功后前端更新购物车图标上的商品数量提示，并弹出成功Toast。
    5.  **查看购物车**: 用户点击导航栏购物车图标进入购物车页。前端请求购物车列表API，渲染购物车内所有商品、数量、价格、选中状态等。
    6.  **调整购物车商品**: 用户在购物车页可以勾选/取消勾选商品，修改商品数量，或删除商品。前端实时更新计算总价，并通过API更新后端购物车状态。
    7.  **去结算**: 用户点击“去结算”按钮。前端进行已勾选商品的库存和价格校验，校验通过后跳转至订单确认页。
    8.  **确认订单信息**: 在订单确认页，前端请求用户收货地址列表，展示已有的地址供选择，若无地址则引导添加。同时，请求可用的优惠券列表供选择，并根据选择计算最终支付金额。
    9.  **提交订单**: 用户确认所有信息无误后，点击“提交订单”按钮。前端通过API将订单详情（商品清单、收货地址、支付方式、优惠券等）发送至后端，成功后后端返回订单号。
    10. **支付流程**: 前端收到订单号后，根据后端提供的支付URL或支付所需参数，引导用户进行支付（如跳转到第三方支付平台）。支付成功后，前端接收支付回调或主动查询支付结果。
    11. **订单完成**: 支付成功后，前端跳转至支付成功页或订单列表页，并提示用户订单已完成。

**4.2 表单校验规则**

*   **统一校验库**: 推荐使用`vee-validate`或`async-validator`等成熟的校验库。
*   **注册/登录表单**:
    *   **手机号**: 必填，11位数字，匹配中国手机号正则 `^1[3-9]\d{9}$`。
    *   **密码**: 必填，长度6-16位，必须包含数字、大小写字母中至少两种。
    *   **确认密码**: 必填，与密码字段保持一致。
    *   **图形验证码**: 必填，4位字母或数字。
    *   **短信验证码**: 必填，6位数字。
*   **收货地址表单**:
    *   **收货人姓名**: 必填，2-20位中英文或字符。
    *   **手机号码**: 必填，11位数字，匹配中国手机号正则。
    *   **省/市/区**: 必选，下拉选择或级联选择。
    *   **详细地址**: 必填，5-50位中英文、数字或字符。
*   **商品评价表单**:
    *   **评价内容**: 必填，5-200字。
    *   **评分**: 必填，1-5星。
*   **错误提示**: 校验失败时，在表单元素下方显示红色错误提示信息。

**4.4 页面状态处理**

*   **Loading状态**:
    *   **全屏加载**: 在页面初次加载或进行全局数据提交（如登录、提交订单）时，使用 `Element Plus` 的 `ElLoading` 组件，覆盖整个页面，显示加载动画。
    *   **局部加载**:
        *   **骨架屏 (Skeleton Screen)**: 在商品列表、商品详情、订单列表等内容加载前，显示与页面结构相似的灰色占位骨架屏，减少用户等待焦虑。
        *   **按钮加载**: 提交表单或点击重要操作按钮时，按钮本身显示加载状态（如Spinner），并禁用按钮，防止重复提交。
        *   **区域加载**: 在某个组件或数据区域需要加载时，在该区域内显示`ElLoading`或自定义加载图标。
*   **空状态**:
    *   **列表页无数据**: 当商品列表、订单列表、购物车、收藏夹等无数据时，展示统一的“暂无数据”文字提示，并配以语义化的图标或插画，引导用户进行下一步操作（如“去购物”）。
    *   **搜索无结果**: 搜索结果页无匹配项时，提示“抱歉，没有找到相关商品，请尝试其他关键词”。
*   **错误状态**:
    *   **网络请求失败**:
        *   **全局**: 使用 `ElMessage` 或 `ElNotification` 组件在页面顶部弹出“网络异常，请稍后重试”的提示信息。
        *   **局部**: 在数据请求失败的区域显示“数据加载失败，点击重试”按钮，用户可手动触发重新加载。
    *   **业务逻辑错误**: 当API返回业务错误码时（如库存不足、优惠券已过期），通过`ElMessage`或`ElMessageBox`弹出具体的错误信息，引导用户修正。
    *   **表单校验失败**: 在表单输入框下方实时显示红色的错误提示文字。
    *   **权限不足**: 统一重定向到登录页，或在页面上显示“您无权访问此页面”的友好提示。

**五、API调用方案**

**5.1 API调用封装方案**

*   **基于Axios封装**: 创建一个统一的`request`实例，并进行全局配置和拦截器设置。
*   **统一配置**:
    *   `baseURL`: 后端API的基础URL。
    *   `timeout`: 请求超时时间。
    *   `headers`: 统一设置`Content-Type`等。
*   **请求拦截器**:
    *   **认证信息**: 在每次请求发送前，从Pinia Store中获取用户`token`，并添加到请求头的`Authorization`字段中（如`Bearer ${token}`）。
    *   **Loading显示**: [待确认] 可根据请求数量或特定标记，显示/隐藏全局Loading。
*   **响应拦截器**:
    *   **Loading隐藏**: [待确认] 隐藏全局Loading。
    *   **业务状态码处理**:
        *   `code === 200`: 请求成功，直接返回`response.data`中的业务数据。
        *   `code === 401`: 未登录或Token失效。清除本地Token，跳转至登录页，并提示“登录已过期，请重新登录”。
        *   `code === 403`: 无权限。提示“您没有访问权限”。
        *   其他业务错误码: 统一通过`ElMessage`组件提示`response.data.msg`中的错误信息。
    *   **HTTP状态码处理**:
        *   `status === 2xx`: 正常响应。
        *   `status === 4xx/5xx`: 网络错误、服务器错误等。统一通过`ElMessage`提示“服务异常，请稍后重试”，或根据具体状态码给出更详细提示。
*   **错误处理**: `try-catch`块捕获网络错误、请求超时等异常，统一提示用户。

**5.3 本地Mock方案**

*   **推荐方案**: **Vite Mock 插件 (`vite-plugin-mock`)**
    *   **理由**: Vite生态下的Mock解决方案，易于配置和使用。可以在开发环境中拦截HTTP请求并返回预定义的JSON数据或自定义处理逻辑，无需启动单独的Mock服务器。
    *   **实现方式**: 在项目根目录创建`mock`文件夹，编写`.ts`或`.js`文件定义Mock接口和数据。通过`vite.config.js`配置`vite-plugin-mock`，即可在开发环境无缝使用Mock数据。
    *   **优势**:
        *   与项目开发流程紧密集成，配置简单。
        *   支持热更新，修改Mock数据无需重启服务。
        *   可以模拟各种HTTP方法、状态码和延迟，高度灵活。
        *   便于前端独立开发，减少对后端进度的依赖。

**六、非功能性需求(前端部分)**

**6.1 性能要求**

*   **首屏加载时间**:
    *   **目标**: 理想情况下 <= 2秒，可接受 <= 3秒 (在3G网络模拟环境下)。
    *   **优化策略**:
        *   **代码分割 (Code Splitting)**: 利用路由懒加载 (已在2.4提及) 和组件按需加载，减少首屏加载的JS资源。
        *   **资源压缩**: JS、CSS、HTML文件进行Gzip/Brotli压缩。
        *   **图片优化**: 图片压缩、WebP格式、响应式图片 (`srcset`)。
        *   **关键CSS内联**: 将少量核心CSS内联到HTML中，减少首个请求的渲染阻塞。
        *   **CDN**: 静态资源（图片、JS、CSS）部署到CDN，加速加载。
        *   **预加载/预取 (Preload/Prefetch)**: 对关键资源或后续可能访问的页面进行预加载。
*   **图片懒加载**:
    *   **实现**: 对于视口外的图片，使用`<img>`标签的`loading="lazy"`属性 (浏览器原生支持) 或集成`vue-lazyload`等库，确保图片只在进入视口时才开始加载。
*   **路由懒加载**:
    *   **实现**: 已在2.4节提及，通过`import()`动态导入路由组件。
*   **打包体积控制**:
    *   **按需引入组件库**: Element Plus支持按需导入，只打包使用到的组件。
    *   **Tree Shaking**: 利用Vite/Rollup的Tree Shaking功能，移除未使用的代码。
    *   **依赖优化**: 谨慎引入大型第三方库，选择轻量级替代方案。
    *   **分析工具**: 使用`rollup-plugin-visualizer`等工具分析打包后的依赖体积，针对性优化。

**6.2 兼容性要求**

*   **浏览器支持范围**:
    *   **桌面端**: Chrome (最新2个版本), Firefox (最新2个版本), Edge (最新2个版本), Safari (最新2个版本)。
    *   **移动端**: iOS Safari (最新2个版本), Android WebView (与对应Chrome版本保持一致)。
*   **移动端适配**:
    *   **响应式布局**: 采用CSS媒体查询 (`@media`) 结合Flexbox/Grid布局，针对不同屏幕宽度设计不同的布局和样式。
    *   **视口单位**: 优先使用`vw`/`vh`或`rem`等相对单位进行布局和字体大小设置。
    *   **触摸事件优化**: 确保按钮和可点击区域足够大，优化移动端手势操作体验。
    *   **Viewport设置**: 在HTML的`<head>`中设置`meta name="viewport"`以正确控制视口。

**6.3 用户体验要求**

*   **页面切换动画**:
    *   **实现**: 在`router-view`组件中使用Vue的`<Transition>`组件，为路由切换添加平滑的过渡动画，如淡入淡出或滑动效果，提升页面切换的流畅感。
*   **反馈提示**:
    *   **操作结果**: 使用 `Element Plus` 的 `ElMessage` 组件，在用户完成关键操作（如加入购物车、提交订单、保存设置）后，在页面顶部弹出简洁的成功/失败/警告提示。
    *   **错误提示**: 表单校验失败时，实时在输入框下方显示红色错误信息；API请求失败时，统一通过`ElMessage`提示错误。
    *   **二次确认**: 对于删除、取消订单等不可逆操作，使用 `ElMessageBox` 弹出模态框进行二次确认。
*   **加载骨架屏**:
    *   **实现**: 在数据密集型页面（如商品列表、详情、个人中心）等待数据加载时，不显示空白区域，而是展示与内容结构一致的灰色占位符（骨架屏），提前提供视觉结构，减少用户等待的焦虑感。

## 二、前端技术架构
### 2.1技术栈选型
- 前端框架：Vue 3.3 + TypeScript（类型安全，适配电商业务）
- UI组件库：Vant 4（移动端优先的Vue3组件库，贴合C端场景）
- 状态管理：Pinia 2（Vue官方轻量状态管理）
- 路由：Vue Router 4
- HTTP客户端：Axios 1.6
- 构建工具：Vite 5（快速热更新）
- 辅助工具：PostCSS（样式适配）、vite-plugin-imagemin（图片压缩）

### 2.2项目目录结构
```
src/
├── api/                # API接口封装
│   ├── modules/        # 按模块拆分的接口文件
│   └── request.ts      # 全局请求实例
├── assets/             # 静态资源
├── components/         # 公共组件（导航、商品卡片、骨架屏）
├── hooks/              # 自定义Hooks（权限、请求、表单校验）
├── layouts/            # 布局组件（主布局、空白布局）

├── router/             # 路由配置
├── stores/             # Pinia状态模块

├── App.vue
└── main.ts
```

### 2.3前端状态管理方案
- **全局Store存储（跨页面共享）**：用户登录状态/Token、购物车列表、商品筛选条件、全局UI弹窗状态
- **组件内部状态**：表单输入值、单个组件临时数据（如商品选中规格）、非全局弹窗状态
- 理由：全局状态仅存储跨页面复用数据，避免props drilling，组件内部状态减少全局冗余

### 2.4前端路由设计
- **路由守卫**：全局前置守卫校验登录权限，未登录用户访问受限页面自动跳转登录页并记录回跳路径；登录页独享守卫拦截已登录用户
- **懒加载策略**：所有页面采用动态导入实现路由懒加载，首屏仅加载首页及公共依赖，访问对应页面时才加载对应资源

### 4.1核心交互流程的文字描述
以「已登录用户完成正品验证+下单」为例：

### 4.4 页面状态处理

*   **流程 2：老客复购流程**
    *   进入个人中心 -> 点击“再来一单” -> 商品自动加入购物车 -> 跳转结算页 -> 确认地址 -> 提交订单。
*   **流程 3：优惠券核销流程**
    *   商品详情页 -> 点击“领券” -> Toast 提示领取成功 -> 结算页 -> 自动匹配最优优惠券 -> 用户确认金额 -> 提交。

1.4 页面路由结构

*   **主流程页面**：`/` (首页), `/list` (分类列表), `/product/:id` (详情), `/cart` (购物车), `/checkout` (结算), `/order-success` (成功)

四、前端交互与逻辑

4.1 核心交互流程的文字描述
*   **加入购物车**：用户点击“加入购物车” -> 前端校验 SKU 是否选择 -> 调用 API -> 成功则触发“飞入购物车”动画 -> 更新 Header 购物车角标数量 -> Toast 提示“添加成功”。
*   **提交订单**：用户点击“提交订单” -> 按钮进入 Loading 状态 (禁用重复点击) -> 调用 API -> 成功则跳转 `/order-success` 并清空购物车 Store 中已购商品 -> 失败则恢复按钮状态并展示错误信息。

4.2 表单校验规则
*   **手机号**：`/^1[3-9]\d{9}$/`，必填，失焦校验。
*   **验证码**：6 位数字，必填。
*   **密码**：6-20 位，包含字母和数字，必填。
*   **地址信息**：收件人 (2-20 字)、手机号 (必填)、详细地址 (必填)。
*   **反馈方式**：输入框下方红色文字提示具体错误，提交时若未通过则聚焦第一个错误项。

4.4 页面状态处理
*   **Loading**：
    *   全局：页面切换时使用顶部进度条 (NProgress)。
    *   局部：列表加载使用 Skeleton (骨架屏)，按钮加载使用 Spinner。
*   **空状态 (Empty)**：
    *   购物车/订单列表为空时，展示插画 + 文案“暂无内容” + “去逛逛”按钮。
*   **错误状态 (Error)**：
    *   接口失败：Toast 提示错误信息（如“网络开小差了”）。
    *   页面加载失败：展示“重试”按钮。
    *   403/401：自动跳转登录页。

五、API 调用方案

5.1 API 调用封装方案
*   **基础封装**：基于 Axios 创建实例 `request`，设置 `baseURL` 和 `timeout`。
*   **请求拦截器**：自动携带 `Authorization: Bearer <token>`，若本地无 Token 则不携带。
*   **响应拦截器**：
    *   统一处理 HTTP 状态码 (200 成功)。
    *   处理业务状态码 (如 `code === 401` 触发退出登录逻辑)。
    *   统一错误 Toast 提示。
*   **取消重复请求**：对于搜索输入等高频场景，使用 `AbortController` 取消前一次请求。

5.2 预估需要调用的 API 清单
*   `POST /api/auth/login` - 用户登录
*   `GET /api/products` - 获取商品列表 (query: page, size, category)
*   `GET /api/products/:id` - 获取商品详情
*   `GET /api/cart` - 获取购物车列表
*   `POST /api/cart/items` - 添加商品到购物车
*   `PUT /api/cart/items/:id` - 更新购物车商品数量
*   `DELETE /api/cart/items/:id` - 删除购物车商品
*   `POST /api/orders` - 创建订单
*   `GET /api/user/profile` - 获取用户信息

5.3 本地 Mock 方案
*   **工具**：使用 `Mock.js` 或 `MSW (Mock Service Worker)`。
*   **策略**：
    *   开发环境 (`VITE_MODE=development`) 开启 Mock。
    *   拦截上述 API 路径，返回符合 TypeScript 定义的静态 JSON 数据。
    *   模拟网络延迟 (300ms-800ms) 以测试 Loading 状态。
    *   **注意**：Mock 数据需尽量贴近真实结构，避免后期联调大幅修改代码。

6.1 性能要求

*   **底部导航**：首页、分类、购物车、我的（TabBar）固定在底部，仅在一级页面显示。

**3.2 设计风格与色彩体系**
*   **主色调**：珊瑚粉 (#FF6B6B) - 传达女性活力与美妆感，用于价格、主按钮。
*   **辅助色**：裸粉色 (#F8E2E2) - 用于背景、标签底色。
*   **字体**：苹果方/系统默认无衬线字体。价格数字使用加粗字体突出。
*   **间距**：基于8px栅格系统 (8px, 16px, 24px)。

**3.3 所有页面清单及功能说明**
1.  **首页**：
    *   *核心元素*：顶部搜索、Banner轮播、金刚区（分类图标）、限时秒杀倒计时、瀑布流商品推荐。
    *   *交互*：下拉刷新、上拉加载更多。
2.  **商品详情页**：
    *   *核心元素*：视频/图片轮播、价格（划线价+现价）、优惠券弹窗、SKU规格选择（颜色/容量）、底部悬浮栏（购物车/立即购买）。
    *   *交互*：点击SKU弹出半屏选择器；点击"加入购物车"有飞入动画效果（可选）。
3.  **购物车页**：
    *   *核心元素*：店铺分组列表、商品勾选框、数量加减器、底部结算栏（全选、总价）。
    *   *交互*：左滑商品条目删除（移动端手势）；点击结算校验库存。
4.  **确认订单页**：
    *   *核心元素*：收货地址卡片、商品清单（只读）、支付方式选择、备注输入、提交订单按钮。
    *   *交互*：点击地址跳转地址选择页；点击提交按钮防抖。
5.  **个人中心**：
    *   *核心元素*：用户头像/昵称、订单状态待支付/待发货/待收货、常用功能入口（优惠券/收货地址/客服）。

#### 四、前端交互与逻辑

**4.1 核心交互流程的文字描述**
以“购买口红”为例：用户在首页看到口红推荐，点击进入详情页。详情页自动展示默认规格（色号#01），用户点击色号轮播图切换到#02，页面价格无变动（假设同价），用户点击“加入购物车”。底部弹出SKU确认框（防止误触），用户确认后，调用接口更新购物车数据，首页TabBar上的购物车图标角标数字+1，并弹出Toast“添加成功”。

**4.2 表单校验规则**
*   **登录**：手机号为11位数字，必填；验证码为4-6位数字，必填。
*   **收货地址**：联系人、手机号、详细地址必填；手机号需符合正则格式。
*   **提交订单**：必须选中有效收货地址。

**4.3 前端数据模型**
*   `Product` : `{ id, name, mainImage, price, originalPrice, sales, skuList }`
*   `CartItem` : `{ skuId, productId, count, specInfo: [], stock }`
*   `Order` : `{ orderId, totalAmount, status: 0|1|2, address: {} }`

**4.4 页面状态处理**
*   **Loading**：首次进入页面或点击加载更多时，展示占位骨架屏；按钮操作时，按钮变灰并显示Loading转圈。
*   **空状态**：购物车为空时，展示插图与“去逛逛”按钮；搜索无结果时，展示“换个词试试”提示。
*   **错误状态**：接口请求失败（如网络超时），在页面中央展示错误提示图标及“点击重试”按钮。

#### 五、API调用方案

**5.1 API调用封装方案**
*   基于Axios创建实例。
*   **请求拦截器**：自动在Header中注入 `Authorization: Bearer <token>`。
*   **响应拦截器**：统一处理HTTP状态码（如401跳转登录，500提示服务器错误）；业务错误码（如code=1001提示库存不足）通过Toast展示给用户。

**5.2 预估需要调用的API清单**
*   `POST /api/v1/auth/login` : 登录
*   `GET /api/v1/products` : 获取商品列表（分页）
*   `GET /api/v1/products/:id` : 获取商品详情
*   `GET /api/v1/cart` : 获取购物车
*   `POST /api/v1/cart/add` : 加入购物车
*   `POST /api/v1/orders` : 创建订单
*   `GET /api/v1/user/address` : 获取地址列表

**5.3 本地Mock方案**
*   使用 **Vite Plugin Mock** 或 **MSW (Mock Service Worker)**。
*   在 `mock/` 目录下编写简单的JSON数据，模拟上述API的响应，确保前端开发不阻塞。

#### 六、非功能性需求(前端部分)

**6.1 性能要求**
*   **首屏加载**：LCP (最大内容绘制) 时间控制在 2.5s 以内。
*   **图片优化**：所有商品图使用WebP格式，开启懒加载。
*   **打包体积**：Gzip压缩后体积控制在 500KB 以内（排除第三方库）。

**6.2 兼容性要求**
*   **移动端适配**：使用 `viewport` 单位 (vw/vh) 或 `rem` 适配不同尺寸手机屏幕。
*   **浏览器支持**：iOS Safari 12+, Android Chrome 70+, 微信内置浏览器。

**6.3 用户体验要求**
*   **页面切换**：路由切换需有平滑的转场动画（如右侧滑入）。
*   **反馈提示**：所有异步操作（加购、提交）必须有明确的 Loading 或 成功/失败 反馈。
*   **点击区域**：移动端可点击元素热区不小于 44x44 px。
